TOKIT 플랫폼은 이더리움 블록체인의 Low-TPS 한계(약 15 TPS) 및 가스비(Gas Fee) 한계를 극복하기 위해 오프체인 인메모리 매칭 엔진과 비동기 온체인 결산 파이프라인을 융합했습니다.

📌 시스템 주요 7대 구성 요소를 전수 분석한 아키텍처 명세:

1. Next.js Client Layer: Idempotency Key (`X-Idempotency-Key`) 헤더를 자동 탑재하며, WebSocket/SSE를 통해 서버 상태와 동기화되는 UI 상태 관리 적용.
2. Spring Boot 4.0 Core Layer: Java 25 `record` 구조를 활용해 불변 DTO를 전면 적용하고, Hexagonal/DDD 레이어링으로 모듈 간 결합도를 최소화.
3. PostgreSQL 17 RDBMS: 모든 자산과 거래 내역이 엄격한 데이터 무결성 하에 저장되는 오프체인 유일 원장 (Source of Truth).
4. Redis 7 In-Memory Engine: 가격-시간 우선순위(Price-Time Priority)를 O(log N)으로 유지하는 Sorted Set 기반 인메모리 호가창 및 AOP 멱등성 분산 락 전용 케시.
5. RabbitMQ 4 Messaging Queue: 매칭 엔진 연산과 RDBMS 반영, 온체인 Web3j 트랜잭션 수신 간의 비동기 이벤트를 디커플링(Decoupling)하여 시스템 처리율 극대화.
6. Spring Batch 5 Engine: 대용량 주주 대상 원화 배당금 절사 지급 및 영업일 정기 온-오프체인 데이터 대사를 담당하는 Chunk 지향 처리 엔진.
7. Hardhat EVM Blockchain: 법적 규제를 준수하는 ERC-1400 Security Token Standard 스마트 컨트랙트로, KYC 완료 주주 지갑 주소만 파티션 간 이체를 허용.

CH 3. 동시성 제어 & 잔액 무결성 아키텍처 (`WalletRepository.java` & `WalletService.java`) Concurrency Control
Pessimistic Write Locking

1) 비관적 배타 락(PESSIMISTIC_WRITE)을 통한 예치금 차감 무결성 전수 코드 해설

동시에 두 개 이상의 주문이나 이체 요청이 들어왔을 때 잔액 오차가 발생하는 것을 막기 위해 DB 레벨의 SELECT ... FOR UPDATE 쿼리를 수행하는 전수 소스코드입니다. 

package com.tokit.domain.wallet.repository;

import com.tokit.domain.wallet.entity.Wallet;
import jakarta.persistence.LockModeType;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Lock;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;
import java.util.List;
import java.util.Optional;

public interface WalletRepository extends JpaRepository<Wallet, Long> {

    List<Wallet> findByUserId(Long userId);

    @Query("SELECT w FROM Wallet w WHERE w.user.id = :userId AND w.asset.id = :assetId")
    Optional<Wallet> findAssetWalletByUserIdAndAssetId(@Param("userId") Long userId, @Param("assetId") Long assetId);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT w FROM Wallet w WHERE w.user.id = :userId AND w.asset IS NULL")
    Optional<Wallet> findKrwWalletByUserIdWithPessimisticLock(@Param("userId") Long userId);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT w FROM Wallet w WHERE w.user.id = :userId AND w.asset.id = :assetId")
    Optional<Wallet> findAssetWalletByUserIdAndAssetIdWithPessimisticLock(
        @Param("userId") Long userId, 
        @Param("assetId") Long assetId
    );
}
💡 코드 상세 라인 튜닝 해설:
• findKrwWalletByUserIdWithPessimisticLock: `w.asset IS NULL` 조건은 사용자의 원화(KRW) 예치금 지갑을 식별하며, `@Lock(LockModeType.PESSIMISTIC_WRITE)` 어노테이션에 의해 하이버네이트는 DB 엔진(PostgreSQL)에 `SELECT ... FOR UPDATE` 배타 락 쿼리를 날립니다.
• 트랜잭션이 완료(Commit)되거나 롤백(Rollback)되기 전까지 다른 스레드는 해당 Row에 접근할 수 없으므로, **동시 잔액 차감에서 발생하는 갱신 손실(Lost Update) 및 음수 잔액 사고를 100% 방지**합니다.
CH 4. AOP 기반 Redis 분산 락 & 멱등성 보장 엔진 (`IdempotencyAspect.java`) AOP & Distributed Lock
Idempotency & SETNX Engine

`@Idempotent` 어노테이션과 Redis `SETNX` 선점 처리 전체 소스코드 분석

클라이언트 요청 시 HTTP 헤더의 `X-Idempotency-Key`를 가로채어 Redis 락을 거는 AOP 구현부 전체 코드입니다. 

package com.tokit.global.aspect;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.tokit.global.dto.ApiResponse;
import jakarta.servlet.http.HttpServletRequest;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.stereotype.Component;
import org.springframework.web.context.request.RequestContextHolder;
import org.springframework.web.context.request.ServletRequestAttributes;
import java.time.Duration;

@Aspect
@Component
@RequiredArgsConstructor
@Slf4j
public class IdempotencyAspect {

    private final StringRedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;
    private static final String HEADER_KEY = "X-Idempotency-Key";
    private static final String PROCESSING = "PROCESSING";

    @Around("@annotation(com.tokit.global.annotation.Idempotent)")
    public Object checkIdempotency(ProceedingJoinPoint joinPoint) throws Throwable {
        ServletRequestAttributes attributes = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
        if (attributes == null) return joinPoint.proceed();

        HttpServletRequest request = attributes.getRequest();
        String idempotencyKey = request.getHeader(HEADER_KEY);

        if (idempotencyKey == null || idempotencyKey.trim().isEmpty()) {
            return ResponseEntity.badRequest()
                    .body(ApiResponse.error(HttpStatus.BAD_REQUEST.value(), "Missing X-Idempotency-Key header"));
        }

        String redisKey = "idempotency:" + idempotencyKey;

        // 1. SETNX 키 선점 (120초 만료 시간)
        Boolean isSet = redisTemplate.opsForValue().setIfAbsent(redisKey, PROCESSING, Duration.ofSeconds(120));

        if (Boolean.FALSE.equals(isSet)) {
            String value = redisTemplate.opsForValue().get(redisKey);
            if (PROCESSING.equals(value)) {
                return ResponseEntity.status(HttpStatus.CONFLICT)
                        .body(ApiResponse.error(HttpStatus.CONFLICT.value(), "이미 처리 중인 요청입니다."));
            } else {
                // 성공 완료된 이전 응답 JSON 캐시를 그대로 재반환 (멱등성 보장)
                return ResponseEntity.ok(objectMapper.readValue(value, ApiResponse.class));
            }
        }

        // 2. 컨트롤러 및 서비스 비즈니스 로직 실행
        Object result;
        try {
            result = joinPoint.proceed();
        } catch (Exception e) {
            // 비즈니스 예외 발생 시 선점 키 삭제 (사용자의 정당한 즉시 재시도 유도)
            redisTemplate.delete(redisKey);
            throw e;
        }

        // 3. 정상 성공 시 결과를 JSON 직렬화하여 10분간 캐싱
        if (result instanceof ResponseEntity<?> responseEntity) {
            if (responseEntity.getBody() instanceof ApiResponse<?> apiResponse) {
                String jsonResult = objectMapper.writeValueAsString(apiResponse);
                redisTemplate.opsForValue().set(redisKey, jsonResult, Duration.ofMinutes(10));
            }
        }

        return result;
    }
}
💡 창의적 백엔드 구현 노하우 (면접 필살기 어필 포인트):
1. Redis SETNX Atomicity: `setIfAbsent`를 이용해 원자적(Atomic) 키 생성을 보장합니다.
2. State Caching Pattern: 처리가 완료된 요청은 결과 DTO JSON을 10분간 저장해두어, 동일 키로 다시 요청이 오면 컨트롤러나 DB 연산 없이 즉시 이전 200 OK 응답을 리턴합니다.
3. Exception Cleanup: 예외 발생 시 `catch` 블록에서 `redisTemplate.delete(redisKey)`를 호출하여 락을 즉시 해제함으로써, 유저가 잘못 입력한 요청 수정 후 즉각 재시도할 수 있도록 세심하게 설계했습니다.

@Transactional
public User signUp(String email, String name, String walletAddress) {
    return userRepository.findByEmail(email)
            .orElseGet(() -> {
                User newUser = userRepository.save(User.builder()
                        .email(email)
                        .name(name)
                        .walletAddress(walletAddress)
                        .build());

                // 기본 원화 예치금 지갑 자동 개설 (1,000만 KRW 시딩)
                walletRepository.save(Wallet.builder()
                        .user(newUser)
                        .asset(null)
                        .balance(BigDecimal.valueOf(10000000.0))
                        .lockedBalance(BigDecimal.ZERO)
                        .build());

                // 대표 토큰증권 보유 지갑 개설 및 1,000 STO 초기 보유량 시딩
                List<String> defaultSymbols = List.of("HDYT", "GNPM", "BSND", "JJIS");
                for (String symbol : defaultSymbols) {
                    assetRepository.findBySymbol(symbol).ifPresent(asset -> {
                        walletRepository.save(Wallet.builder()
                                .user(newUser)
                                .asset(asset)
                                .balance(BigDecimal.valueOf(1000.0))
                                .lockedBalance(BigDecimal.ZERO)
                                .build());
                    });
                }
                return newUser;
            });
}

@Transactional
public User updateKycStatus(Long id, boolean kycStatus) {
    User user = getUserById(id);
    user.updateKycStatus(kycStatus);
    
    // 스마트 컨트랙트 규제 상 화이트리스트 동기화
    if (kycStatus) {
        contractService.addToWhitelist(user.getWalletAddress());
    } else {
        contractService.removeFromWhitelist(user.getWalletAddress());
    }
    return user;
}
CH 6. 공모 청약 모집 엔진 & BigDecimal 금융 연산 (`AssetService.java`) Primary Market
Subscription Math

공모 청약 모집금 달성률 연산 & BigDecimal 정밀 계산 소스코드

청약 신청 시 예치금을 비관적으로 차감하고 STO 토큰 잔고를 배정하며 온체인의 transferByPartition을 실행하는 흐름입니다. 

@Transactional
public void subscribeAsset(Long userId, String symbol, BigDecimal amount) {
    Asset asset = getAssetBySymbol(symbol);
    User user = userService.getUserById(userId);

    // 1. 예치금 차감 (비관적 락)
    Wallet krwWallet = walletRepository.findKrwWalletByUserIdWithPessimisticLock(userId)
            .orElseThrow(() -> new IllegalArgumentException("KRW 지갑을 찾을 수 없습니다."));
            
    if (krwWallet.getBalance().compareTo(amount) < 0) {
        throw new IllegalArgumentException("청약 신청 예치금이 부족합니다.");
    }
    
    krwWallet.updateBalance(krwWallet.getBalance().subtract(amount), krwWallet.getLockedBalance());

    // 2. STO 토큰 배정 및 보유 잔고 증액
    Wallet tokenWallet = walletRepository.findAssetWalletByUserIdAndAssetIdWithPessimisticLock(userId, asset.getId())
            .orElseGet(() -> walletRepository.save(Wallet.builder().user(user).asset(asset).balance(BigDecimal.ZERO).lockedBalance(BigDecimal.ZERO).build()));

    tokenWallet.updateBalance(tokenWallet.getBalance().add(amount), tokenWallet.getLockedBalance());

    // 3. 공모 모집 달성액 증액 (@Version Optimistic Lock 적용)
    asset.updateRecruitedAmount(asset.getRecruitedAmount().add(amount));

    // 4. ERC-1400 온체인 수량 배정 전송
    contractService.handleTransferByPartition(symbol, "DEFAULT", contractService.getOwnerAddress(), user.getWalletAddress(), amount);
}

@Configuration
@Slf4j
public class DividendBatchConfig {

    private final WalletRepository walletRepository;
    private final DividendPayoutRepository dividendPayoutRepository;
    private final DividendPayoutDetailRepository dividendPayoutDetailRepository;

    public DividendBatchConfig(@Lazy WalletRepository walletRepository,
                               @Lazy DividendPayoutRepository dividendPayoutRepository,
                               @Lazy DividendPayoutDetailRepository dividendPayoutDetailRepository) {
        this.walletRepository = walletRepository;
        this.dividendPayoutRepository = dividendPayoutRepository;
        this.dividendPayoutDetailRepository = dividendPayoutDetailRepository;
    }

    @Bean
    @JobScope
    public Step dividendStep(JobRepository jobRepository, PlatformTransactionManager transactionManager,
                             ItemReader<Wallet> dividendReader,
                             ItemProcessor<Wallet, DividendPayoutDetail> dividendProcessor,
                             ItemWriter<DividendPayoutDetail> dividendWriter) {
        return new StepBuilder("dividendStep", jobRepository)
                .<Wallet, DividendPayoutDetail>chunk(10, transactionManager)
                .reader(dividendReader)
                .processor(dividendProcessor)
                .writer(dividendWriter)
                .build();
    }

    @Bean
    @StepScope
    public ItemProcessor<Wallet, DividendPayoutDetail> dividendProcessor(@Value("#{jobParameters['payoutId']}") Long payoutId) {
        DividendPayout payout = dividendPayoutRepository.findById(payoutId).orElseThrow();
        BigDecimal totalDividend = payout.getTotalDividendAmount();
        BigDecimal totalSupply = payout.getAsset().getTotalSupply();

        return wallet -> {
            BigDecimal userTokenBalance = wallet.getBalance().add(wallet.getLockedBalance());
            // 1. 지분율 연산 (소수점 6자리 반올림)
            BigDecimal shareRatio = userTokenBalance.divide(totalSupply, 6, RoundingMode.HALF_UP);
            // 2. 배당 금액 계산 및 소수점 이하 원화 절사 (RoundingMode.DOWN)
            BigDecimal payoutAmount = totalDividend.multiply(shareRatio).setScale(0, RoundingMode.DOWN);

            return DividendPayoutDetail.builder()
                    .payout(payout)
                    .user(wallet.getUser())
                    .walletAddress(wallet.getUser().getWalletAddress())
                    .shareRatio(shareRatio)
                    .payoutAmount(payoutAmount)
                    .status("PENDING")
                    .build();
        };
    }

    @Bean
    @StepScope
    public ItemWriter<DividendPayoutDetail> dividendWriter() {
        return chunk -> {
            for (DividendPayoutDetail detail : chunk.getItems()) {
                try {
                    // 유저의 KRW 예치금 지갑을 비관적 배타 락(PESSIMISTIC_WRITE)으로 조회 후 증액
                    Wallet krwWallet = walletRepository.findKrwWalletByUserIdWithPessimisticLock(detail.getUser().getId()).orElseThrow();
                    krwWallet.updateBalance(krwWallet.getBalance().add(detail.getPayoutAmount()), krwWallet.getLockedBalance());
                    walletRepository.save(krwWallet);

                    detail.updateStatus("SUCCESS", null);
                } catch (Exception e) {
                    detail.updateStatus("FAILED", e.getMessage());
                }
            }
            dividendPayoutDetailRepository.saveAll(chunk.getItems());
        };
    }
}

RDBMS 오프체인 잔고 vs 스마트 컨트랙트 `balanceOfByPartition` 교차 대조 전체 코드

일일 배치 구동 시 잔고 불일치를 감지하여 DB 영속화 및 Slack/Admin SSE 실시간 적색 토스트를 송출하는 전수 코드입니다. 

@Bean
public ItemProcessor<Wallet, ReconciliationLog> walletProcessor() {
    return wallet -> {
        String walletAddress = wallet.getUser().getWalletAddress();
        String symbol = wallet.getAsset().getSymbol();
        
        // 1. DB 상의 오프체인 보유량
        BigDecimal offchainBalance = wallet.getBalance().add(wallet.getLockedBalance());
        
        // 2. 스마트 컨트랙트 온체인 잔고 조회 (DEFAULT 파티션)
        BigDecimal onchainBalance = contractService.balanceOfByPartition(symbol, "DEFAULT", walletAddress);
        
        // 3. 대조 연산
        BigDecimal difference = offchainBalance.subtract(onchainBalance).abs();
        if (difference.compareTo(BigDecimal.ZERO) == 0) {
            return null; // 잔고 일치 시 로그를 저장하지 않고 스킵
        }
        
        return ReconciliationLog.builder()
                .user(wallet.getUser())
                .asset(wallet.getAsset())
                .walletAddress(walletAddress)
                .offchainBalance(offchainBalance)
                .onchainBalance(onchainBalance)
                .difference(difference)
                .checkedAt(LocalDateTime.now())
                .build();
    };
}

Web3j `Sign.recoverFromSignature` 서명자 복원 & Nonce 잠금 전수 코드

사용자 개인키 노출 없이 오프체인 메시지 서명(from:to:symbol:amount:nonce)을 복원하여 가스비를 대납하는 수선 소스코드입니다. 

@Transactional
public void verifySignatureAndTransfer(
        String fromAddress, String toAddress, String assetSymbol,
        BigDecimal amount, Long nonce, String signature
) {
    String lowerFrom = fromAddress.toLowerCase();
    RelayerNonce relayerNonce = relayerNonceRepository.findById(lowerFrom).orElseGet(...);

    // 1. DB 기반 오프체인 Nonce 검증 (재플레이 공격 차단)
    if (!relayerNonce.getNextNonce().equals(nonce)) {
        throw new IllegalArgumentException("유효하지 않은 논스 값입니다.");
    }

    String plainMessage = lowerFrom + ":" + toAddress.toLowerCase() + ":" + assetSymbol + ":" + amount.stripTrailingZeros().toPlainString() + ":" + nonce;

    // 2. Ethereum personal_sign 서명 복원 검증
    if (!verifyEthereumSignature(plainMessage, signature, fromAddress)) {
        throw new IllegalArgumentException("전자서명 인증 실패");
    }

    relayerNonce.incrementNonce();
    relayerNonceRepository.save(relayerNonce);

    // 3. 오프체인 잔액 이동 & Web3j forceTransferByPartition 대납 트랜잭션 발송
    contractService.handleTransferByPartition(assetSymbol, "DEFAULT", fromAddress, toAddress, amount);
}
CH 11. JPA N+1 문제 해결 & 쿼리 성능 최적화 디테일 (`PostRepository.java` & `CommunityService.java`) JPA Query Optimization
Fetch Join & Pagination Query Separation

`LEFT JOIN FETCH`와 `countQuery` 명시적 분리 튜닝 전체 코드 분석

커뮤니티 게시글 목록 페이징 조회 시 연관된 User 및 Asset 엔티티를 N+1 쿼리 없이 단 1번의 DB 쿼리로 조회하도록 튜닝한 핵심 구현부입니다. 

package com.tokit.domain.community.repository;

import com.tokit.domain.community.entity.Post;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface PostRepository extends JpaRepository<Post, Long> {

    @Query("SELECT p FROM Post p LEFT JOIN FETCH p.user LEFT JOIN FETCH p.asset WHERE p.asset.id = :assetId")
    Page<Post> findByAssetId(@Param("assetId") Long assetId, Pageable pageable);

    @Query(value = "SELECT p FROM Post p LEFT JOIN FETCH p.user LEFT JOIN FETCH p.asset",
           countQuery = "SELECT count(p) FROM Post p")
    Page<Post> findAllWithUserAndAsset(Pageable pageable);
}
💡 N+1 쿼리 최적화 튜닝 해설:
• N+1 발생 상황: `@ManyToOne` 관계인 `Post -> User`, `Post -> Asset`을 지연 로딩(Lazy Loading)으로 둘 경우, 게시글 10개를 조회하면 작성자 유저 10번, 자산 10번 조회가 나가 총 1+20번의 DB 쿼리가 낭비됩니다.
• JOIN FETCH 해결: `LEFT JOIN FETCH p.user LEFT JOIN FETCH p.asset`을 사용해 단 1번의 조인 쿼리로 연관 객체를 한 번에 영속성 컨텍스트에 땡겨옵니다.
• countQuery 분리 극복: Spring Data JPA에서 `FETCH JOIN`과 `Pageable`을 함께 쓰면 하이버네이트가 메모리 페이징(In-Memory Pagination)을 수행하여 OOM 경고를 띄우는데, `countQuery = "SELECT count(p) FROM Post p"` 구문을 분리 명시하여 DB 레벨 안전 페이징을 구현했습니다.

🔥 Issue 1. 비동기 스레드 전환 시 LazyInitializationException 해결
RabbitMQ Worker로 체결 이벤트를 넘길 때 JPA Persistence Context 종료 이슈를 엔티티 대신 Record DTO(`TradeEventDto`) 프로젝션으로 발행하여 완전 극복.
🔥 Issue 2. Web3j 온체인 Nonce 멀티스레드 충돌 극복
온체인 RPC `eth_getTransactionCount` 직접 조회의 동시성 한계를 DB `relayer_nonces` 비관적 락 테이블 관리로 해결하여 온체인 Nonce 거부율 0% 달성.
🔥 Issue 3. 자바 double 부동소수점 단수차 0.000001원 원화 누적 오차
전 코범위 `BigDecimal` 통일 및 `setScale(0, RoundingMode.DOWN)` 원화 이하 절사 규격화로 금융 팽창 방지.
🔥 Issue 4. Spring Batch와 Repository 간 빈 순환 참조(Circular Dependency)
Batch Config 생성자에 `@Lazy` 어노테이션을 부여하여 지연 주입 유도로 애플리케이션 기동 실패 극복.
🔥 Issue 5. 호가창(STOMP WebSocket) vs 체결내역(SSE) 프로토콜 이원화 파이프라인
잦은 양방향 갱신이 필요한 호가창판은 STOMP WebSocket(`/topic/orderbook/{symbol}`)으로 연동하고, 서버 단방향 푸시만 필요한 체결 내역은 SSE(`GET /api/trades/subscribe/{symbol}`)로 채널을 분리해 커넥션 오버헤드 최적화.
🔥 Issue 6. Flyway 데이터베이스 버전 관리 및 스키마 자동 마이그레이션
개발진 간 PostgreSQL 스키마 불일치를 해결하기 위해 `V1__init_schema.sql` 스크립트를 작성하고 Flyway 마이그레이션을 애플리케이션 기동 시 자동 정렬하도록 구축.

Q1. 동시 다발적인 예치금 충전/차감에서 잔액 오차를 방지한 기법은 무엇인가요?
"TOKIT STO 거래소는 금융 데이터 무결성을 위해 충전/차감 시 DB 레벨의 비관적 배타 락(SELECT ... FOR UPDATE)을 획득하여 순차 트랜잭션을 집행했습니다. 또한 요청 헤더의 X-Idempotency-Key를 AOP와 Redis 분산 락(SETNX 120초)으로 선점 처리하여 동일 요청 연타나 재전송으로 인한 이중 결제를 원천 차단했습니다."
Q2. 온-오프체인 데이터 간 불일치는 어떻게 감지하나요?
"매 영업일 밤 실행되는 Spring Batch 기반 일일 데이터 대사(Daily Reconciliation Batch)가 PostgreSQL RDBMS 지갑 잔액과 Web3j 온체인 balanceOfByPartition을 1:1 대조합니다. 단 0.1 수량이라도 오차가 감지되면 즉시 Slack Alert 및 Admin SSE 적색 경보 팝업을 전송하여 관측 가능성을 확보했습니다."
Q3. JPA N+1 문제 해결 경험을 설명해주세요.
"커뮤니티 게시글 목록 조회 시 게시글마다 작성자 User 및 연관 Asset을 지연 로딩할 때 발생하는 N+1 문제를 방지하고자 LEFT JOIN FETCH 구문을 적용했습니다. 아울러 Spring Data JPA 페이징 처리 시 하이버네이트의 메모리 페이징 경고를 방지하기 위해 countQuery를 명시적으로 분리 작성하여 DB 레벨 최적화를 달성했습니다."
Q4. 가스비 대납 메타 트랜잭션(Relayer)의 구현 원리는 무엇인가요?
"투자자의 개인키 노출 없이 메타마스크 personal_sign 오프체인 서명 메시지를 받아 백엔드 RelayerService에서 Web3j Sign.recoverFromSignature로 오프체인 서명자를 복원 및 검증했습니다. 이후 DB 관리 relayer_nonces 테이블에 비관적 락을 걸어 트랜잭션 재플레이 공격 및 온체인 Nonce 꼬임을 방지했습니다."
Q5. 대용량 배당금 계산 시 단수차 오차는 어떻게 방지했나요?
"자바 기본 부동소수점(`double`) 대신 전체 금액 연산을 `BigDecimal`로 통일하고, 배당금 산출 시 `BigDecimal.setScale(0, RoundingMode.DOWN)`을 적용하여 소수점 이하 원화 절사 정책을 표준화함으로써 회사 배당 재원을 초과해 지급하는 금융 팽창 사고를 원천 차단했습니다."
